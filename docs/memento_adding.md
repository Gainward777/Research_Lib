# План добавления Memento

## 1. Цель

Memento превращает Research Library в общую долговременную память локальных
агентов разработки. Система не заменяет Linear и Git:

- Linear остаётся источником задач, статусов и исполнителей;
- Git остаётся источником кода, веток, коммитов и истории изменений;
- Research Library хранит причины решений, подтверждённые результаты,
  промежуточное состояние реализации и контекст для продолжения работы.

Агенты Codex, Cursor, Claude Code и другие подключаются как внешние MCP-клиенты.
Ни один агент или IDE не устанавливается внутрь Research Library.

## 2. Зафиксированные решения

1. Контекст ищет GBrain по свободному описанию задачи или бага. Старая Linear-задача,
   файл, символ и commit улучшают поиск, но не являются обязательными.
2. Ответ имеет фиксированные блоки и содержит только найденные материалы:
   `related_implementations`, `decisions`, `known_problems`,
   `tests_and_evidence`, `checkpoints`.
3. Записи Memento неизменяемы. Исправление публикуется новой записью с указанием
   `supersedes_item_id`.
4. На уровне MCP используются только две новые операции:
   `library_get_context` и `library_publish_context`.
5. Linear-задачи не копируются в библиотеку. Сохраняется только ссылка
   `work_item`, если она известна.
6. Нет ACL отдельных документов. Токен получает целостный контекст доступного
   проекта; права разделяются только на read, publish и admin на уровне проекта.
7. Полные диалоги, terminal history, скрытые рассуждения моделей и секреты не
   сохраняются.
8. Несколько одновременных задач не используют глобальную «текущую задачу».
   Каждая запись привязана к своему `work_item` или временному `work_context_id`.

## 3. Модель данных

В `LibraryItemType` добавляется `development-context`. Страница остаётся обычным
durable Markdown-материалом и индексируется GBrain.

В frontmatter сохраняются:

```yaml
type: development-context
source_kind: agent
metadata:
  context_kind: decision | checkpoint | implementation_snapshot | problem | test_evidence
  project: project-slug
  repository: repository-slug
  work_item: optional Linear ID
  work_context_id: optional temporary ID
  branch: optional branch
  commit: optional commit SHA
  paths: []
  created_by: agent | developer | ci
  verification: unverified | ci-verified | human-approved
  supersedes_item_id: optional library item ID
```

Обязательны `context_kind`, `title` и непустой `content`. `project` можно не
передавать, только если токен имеет ровно один Memento-раздел с publish-доступом;
при нуле или нескольких подходящих разделах он обязателен. Должен быть задан хотя
бы один идентификатор рабочего контекста: `work_item` или `work_context_id`.

## 4. Получение контекста

`library_get_context` принимает свободный `query` и необязательные фильтры:

```json
{
  "query": "Пользователя периодически выбрасывает из системы",
  "project": "platform",
  "repository": "backend-api",
  "work_item": "BUG-731",
  "limit": 20
}
```

GBrain выполняет контекстный поиск по всей истории `development-context`.
Фильтры проекта и репозитория ограничивают пространство поиска, но сведения о
старой задаче, файлах или commit не требуются. Найденные страницы загружаются из
Markdown и детерминированно распределяются по фиксированным блокам. Каждый блок
содержит исходный `item_id`, slug и сохранённые Git/Linear-ссылки.

## 5. Публикация контекста

`library_publish_context` принимает структурированный payload и обязательный
`idempotency_key`. Запись проходит через существующий `ItemService`, поэтому
получает атомарный Markdown, receipt, GBrain-индексацию и retry при ошибке.

Если задан `supersedes_item_id`, сервис проверяет существование старой Memento-записи
и создаёт отношение `continues`; старый Markdown не изменяется и не удаляется.

## 6. Агентные скиллы

В репозитории поставляется переносимый пакет с общей схемой MCP, одним
управляющим и четырьмя узкими скиллами:

- `library-development-workflow` — автоматически определять фазу работы и
  запускать нужный узкий сценарий без ручного контроля разработчика;

- `library-find-context` — найти контекст по свободному описанию;
- `library-record` — сохранить решение, проблему или доказательство;
- `library-checkpoint` — зафиксировать состояние незавершённой работы;
- `library-resume` — восстановить checkpoint и дополнить его поиском GBrain.

Скиллы используют одни и те же два MCP-инструмента. Управляющий скилл не создаёт
параллельную бизнес-логику: он маршрутизирует начало, durable-событие, паузу,
возобновление и завершение в четыре узких сценария. Скиллы не коммитят, не пушат,
не переключают ветки и не выполняют `git stash` без отдельного запроса пользователя.

## 7.1. Актуальный эксплуатационный статус на 2026-09-21

Серверный Memento-инкремент, MCP tools, observability и переносимые агентные
skills реализованы. Автоматизированный пилот выполнен через настоящий Railway
`/mcp`, project-scoped tokens и production GBrain:

- `pilot-agent-a` опубликовал implementation snapshot, decision и checkpoint;
- `pilot-developer-b` восстановил незавершённую задачу, переключился на срочный
  баг и затем вернулся к исходной задаче;
- поиск только по устному описанию бага нашёл реализацию из другой задачи;
- retry с тем же idempotency key вернул тот же item без дубликата;
- новый checkpoint сохранил связь `continues` с предыдущим;
- `control-agent` другого проекта не увидел pilot-контекст и не смог в него
  публиковать;
- пилот выявил и позволил исправить hydration GBrain search hits до применения
  project/repository filters.
- Railway выдал внешний HTTPS endpoint
  `https://researchlib-production.up.railway.app/mcp`;
- внешний `/readyz` отвечает `200`, MCP принимает project-scoped token, а запрос
  без токена отклоняется до передачи в MCP server.

В тестовом окружении теперь есть две pilot-секции, три scoped test tokens и шесть
материалов `development-context`. Управляющий скилл и четыре узких скилла лежат
в `agent-skills/`. Для ввода в реальную работу команд всё ещё остаются
эксплуатационные действия:

- project-specific разделы и токены пока созданы только для pilot, а не для
  настоящих проектов и разработчиков;
- пакет skills ещё не установлен и не настроен в локальных Codex, Cursor и
  Claude Code разработчиков.

Чтобы обновление истории изменений и передача работы между агентами начали
работать по факту, требуется эксплуатационный rollout:

1. Создать `memento/<project>` для каждого подключаемого проекта.
2. Выпустить отдельный project-scoped token каждому разработчику или агенту.
3. Настроить внешний MCP endpoint и токен в локальной агентной среде; установить
   полный пакет из `agent-skills/` и включить implicit invocation для
   `library-development-workflow`.
4. Опубликовать первые подтверждённые implementation snapshots и checkpoints,
   чтобы GBrain получил реальную историю для поиска.
5. Повторить подтверждённый pilot workflow на первой настоящей задаче каждого
   проекта и наблюдать retrieval/ошибки в Grafana.

## 8. Критерии готовности первого инкремента

1. Внешний MCP-клиент публикует `decision`, `checkpoint` или другой Memento-контекст.
2. На диске появляется durable Markdown-страница, индексируемая GBrain.
3. Повтор с тем же idempotency key не создаёт дубликат.
4. Свободный запрос без ссылки на старую задачу находит релевантную историю.
5. Результат содержит фиксированные блоки и ссылки на исходные материалы.
6. Новая версия с `supersedes_item_id` не перезаписывает старую.
7. Существующие Telegram, REST и MCP-сценарии продолжают проходить тесты.
